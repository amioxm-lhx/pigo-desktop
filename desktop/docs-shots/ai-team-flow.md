# AI 军团是怎么跑完一天的

这份是**执行流程**手册：从一个员工被叫醒，到一条线索变成一笔成交，中间每一步是谁在做、依据是什么、东西落在哪张表。产品介绍在 `ai-team-promo.md`，打法在 `ai-team-battle-pack.md`。

---

## 0. 一句话

**你雇的不是一个会聊天的 AI，是一条会自动运转的生产线。** 九个员工各占一个工位，每 30 秒被问一次"到你点了吗"，到点就自己开工；干完的活变成数据库里的行，下一站的员工读那些行接着干。你只在两站出现：**定稿**和**发布**。

---

## 1. 四层结构

| 层 | 是谁 | 干什么 | 碰不碰外部世界 |
| --- | --- | --- | --- |
| 引擎 | 常驻循环（主进程） | 每 30 秒问一次"谁到点了"，把到点的员工叫起来 | 不 |
| 员工 | 7 个干活的人 | 巡站、写稿、投放、接客、跟单、售后 | 是 |
| 中层 | 线索主管、内容主编 | 读看板、下判断、派活、上报 | **不** |
| 老板 | 你 | 定稿、发布、拍板涉钱的事 | 是 |

三条设计规矩，后面所有细节都是它们的推论：

1. **员工之间不互相发消息，只通过看板的行交接。** 写稿的人不认识发布的人，两个人读同一张表。哪天投出去的话说错了，写着"该说什么"的那一行和写着"谁去说"的那一行都还在。
2. **中层不对外说话。** 不发帖、不评论、不发邮件。它只读、判断、派活，派活留成一条带期限的工单。
3. **无人值守的运行绝不闯过 `humanGate`。** 图里放了这道门，跑到这里直接中断（记 `HUMAN_GATE`），不会假装没看见。

## 2. 一天的时钟

排期是每个员工自己的 `schedule_json`，按本地时区（+8）算。下面是库里 9 个在编员工的真实排期：

| 员工 | 身份 | 每天几点 | 日配额 | 派单上限 |
| --- | --- | --- | --- | --- |
| 线索主管 | 中层 | 09:15、16:45 | 2 轮 | 5 件 |
| 侦察员 | 员工 | 09:30、14:30 | 2 轮 | — |
| 跟单员 | 员工 | 09:40、14:40 | 4 轮 | — |
| 地推员 | 员工 | 10:00、15:00 | 4 轮 | — |
| 接线员 | 员工 | 11:30、16:30、21:00 | 3 轮 | — |
| 售后员 | 员工 | 19:30 | 2 轮 | — |
| 选题员 | 员工 | 20:30 | 1 轮 | — |
| 内容主编 | 中层 | 20:45 | 1 轮 | 5 件 |
| 笔杆子 | 员工 | 21:30 | 2 轮 | — |

排期的时间不是随手定的，是**按上下游的先后串起来的**：早上巡站 → 主管上午派活 → 白天两轮投放和三轮接客 → 傍晚跟单 → 晚上售后 → 20:30 选题员读今天的回音 → 20:45 主编定明天的题 → 21:30 笔杆子写稿。第二天早上你醒来时，稿子已经躺在内容工厂等你定稿。

**回音巡检**不在这个表里，它每 **15 分钟**跑一次（应用启动 90 秒后跑第一遍），因为"有没有人回你"这件事不能等一天。

## 3. 一次运行里面发生了什么

引擎叫醒一个员工，叫"领一轮"（claim）。一轮的完整过程：

```
引擎每 30 秒 tick 一次
  → 先把过期的工单关掉（超期限的派单直接标失败，绝不迟到执行）
  → 问宿主：谁到点了？（同时最多放 2 个人进来跑）
  → 领到的每一轮：
       ① 立刻把 next_run_at 推到下一个时段（先推进再跑，中途崩溃也不会同一时段反复重启）
       ② 解析密钥：这个员工用谁的 key、哪个模型（每个员工可以完全不一样）
       ③ 拿到这一轮要走的步骤（工作流的顶点序列）
       ④ 逐步执行，每步：
            · 写一行运行日志（结论 + 完整回复）
            · 如果这一步声明了产出物，把回复里的卡片落库成行
            · 把这一步的结论传给下一步（下一步不是面对一群陌生人）
       ⑤ 如果图里写了交接（handoff），叫醒下一个员工开新的一轮（最多 3 层）
       ⑥ 收尾：succeeded / failed / aborted
```

### 十一种节点

工作流是节点图，节点类型是封闭的（写了不认识的名字直接编译失败，不会跑出一个没人实现的步骤）：

| 节点 | 干什么 |
| --- | --- |
| `trigger` | 排期入口：schedule（定时）/ manual（手动）/ event（被交接触发） |
| `probe` | 巡站。**驱动已经先把页面读好放进上下文**，员工只做判断，不自己爬 |
| `analyze` | 对着一批材料下判断，必须写清"聚焦什么" |
| `produce` | 产出成品，必须写清"产出物是什么"（决定落哪张表） |
| `memory` | 读写共享记忆（read / write / retire） |
| `board` | 读看板 / 下判断 / 派活 / 上报（中层专用） |
| `agent` | 自由一步，必须给指令 |
| `condition` | 分支 |
| `handoff` | 交给另一个员工，触发他的新的一轮 |
| `humanGate` | 人闸。无人值守跑到这里**直接中断** |
| `notify` | 汇报（桌面通知） |

### 四个值得单独说的行为

- **`board read` 不走模型。** 中层要看的看板摘要，是宿主机直接从真实的行里算出来塞进上下文的。原因很实在：中层拿来下判断的数字，必须和你屏幕上看到的数字是同一份。
- **`probe` 是真的不抓取。** 驱动先按站点名读好页面，标好哪几个站点没读到（`skipped`），再交给员工。所以"这轮没读全"是写在汇报里的，不会变成员工自己换个法子去捞。
- **`memory read` 是累加不是覆盖。** 一个员工既读话术又读位置，两批材料都在他面前，不会被后一批挤掉。
- **解析失败的卡片直接丢掉，只记日志。** 一张卡片是关于一个真人的声明，半张解析出来的卡片等于凭空替人说话。宁可这轮少几条，也不猜。

## 4. 一条线索的十站

流水线页面上的十站，就是这条线索要走完的路。每一站的颜色告诉你球在谁手上：

| 站 | 名字 | 谁 | 产出物 | 颜色 |
| --- | --- | --- | --- | --- |
| 1 | 巡站 | 侦察员 | 读到的页面（**当次用完即弃，不落库**） | 机器 |
| 2 | 分级 | 线索主管 | 线索卡（打分、分列） | 机器 |
| 3 | 选题 | 选题员 | 待回答的问题清单 | 机器 |
| 4 | 写稿 | 笔杆子 | 稿件（多版 A/B 备选） | 机器 |
| 5 | **定稿** | **你** | 通过 / 驳回 | **你** |
| 6 | **发布** | **你** | 发布链接 | **你** |
| 7 | 回音 | 回音巡检 | 回复数、走势、陌生人的卡片 | 机器 |
| 8 | 接洽 | 接线员 | 意向分级 | 机器 |
| 9 | 成交 | 跟单员 | 报价 / 合同 / 打款记录 | 机器 |
| 10 | 交付 | 售后员 | 交付记录、口碑 | 机器 |

中间那两站——**定稿和发布**——不属于任何员工。这是整条链上只有你才能按的两个按钮，也是所有卡片都带状态颜色的原因。

### 一条线索实际的样子

1. **侦察员**巡站时，驱动已经把页面读好了。他从里面挑出"自己就是决策人、原话里有第一人称的获客动作、而我们答得上来"的人，写成线索卡落库。三条缺一条就丢，宁可这轮一条不留。
2. **线索主管**上午读线索看板，判断先动哪一条、用什么角度、派给谁，派出去的活变成一条带期限的工单。
3. **选题员**晚上把一线原话按"会不会买"分类，产出待回答的问题清单。
4. **笔杆子**读当天选题，为每个题目写 2–3 个不同开头的版本作为 A/B 备选，落库成稿件（状态 `draft`）。
5. **你**在今日页点"定稿批准"（`review`/`draft` → `approved`），再点"发布"（`approved` → `queued`）。两下都不跳页、都不用填地址。之后发出去这一步，谁发谁回填地址（`queued` → `published`）：你自己发，或在内容工厂那一列点「标记已投放」。
6. **回音巡检**从这一刻开始每 15 分钟读一次这条链接。
7. 有人回复 → 变成一张**新的线索卡**（在 `replied` 列），交给**接线员**问预算和卡点。
8. 值得跟的 → **跟单员**推进试用、报价、合同、打款。
9. 成交后 → **售后员**交付、回访、要口碑，客户的真实原话又变成下一轮写作的素材。

**注意第 7 步**：陌生人回你一句，系统就当他是一条线索。这是这套东西唯一一个会自动长出线索的地方，也是它从"发内容"变成"做生意"的转折点。

## 5. 中层做的两件事

中层和普通员工在结构上没有区别——同样的密钥、同样的工作流、同样的日志和记忆。它是中层，只因为它的图里多了两样东西：一个 `board` 节点，和那个节点被授权派活给谁。

| | 线索主管 | 内容主编 |
| --- | --- | --- |
| 看哪张板 | 线索看板 | 内容看板 |
| 一天几轮 | 09:15、16:45 | 20:45 |
| 能派给谁 | 笔杆子、地推员、接线员、跟单员 | 笔杆子、地推员 |
| 能派的活 | 写稿、投放、接客、跟单 | 写稿、投放 |
| 一天最多派 | 5 件 | 5 件 |

### 下判断 → 派活

中层读完看板，做两件事：

- **派活**（`judge`）：生成工单——派给谁、做什么、为什么是现在、多久内要完成。**工单是排队，不是当场执行**：调度器下一轮才把那个员工叫起来。所以"主管要求了"和"员工做了"是两条可以事后对照的事实，而不是一团糊在一起的动作。
- **上报**（`report`）：只把**你必须亲自定**的写进建议箱——涉及钱（报价、折扣、预算）、涉及对外承诺、涉及改口径。没有就明确写"这轮没有要你定的"，不会为了显得在干活硬凑。

### 四道刹车

无人值守的自反馈环是最容易失控的东西，所以派活这条路被卡得很紧：

1. 只能派给**自己图里点名的人**（换个员工名字？授权表也跟着数据走，改名不影响）。
2. 只能派**自己图里声明的动词**。
3. **一天最多 5 件**。这是唯一的刹车——因为**派活不需要你批**（你之前定的：限次数就行）。
4. 工单有**期限**（默认 6 小时，你可以在 1–48 小时之间调）。过期的工单直接标失败，**绝不迟到执行**——一条过期的留言发到一个已经翻篇的帖子里，比不发更糟，而且你永远不会知道中层的计划已经馊了。

## 6. 回音怎么回来

这是整条链上最容易做成假的环节，所以单独讲。回音巡检（watch）每 15 分钟做一次：

1. **挑出值得再看一眼的稿子**：已发布、并且有链接的。
2. **读回页面**：这条稿子自己的回复数、它那个话题今天的走势。
3. **每个陌生人一条线索卡。**

三个细节是为了让这件事**不骗人**：

- **靠指纹认自己。** 站点不会告诉你"你那条评论的 id 是多少"，所以用发布正文去掉空白后的**前 20 个字符**当指纹，去页面上找自己。够长到同一篇文章下的两条评论不会撞，够短到站点裁剪或重排结尾也还认得出来。
- **数字掉了就照写，不做减法。** 回复数从 12 变成 10，写 10。删掉的回复不等于负需求，账要如实记。
- **同一张卡只产生一次。** 去重键是（站点 + 作者 + 原话）。所以每 10 分钟跑一遍不会把同一个人灌满你的看板。

## 7. 你要拍板的只有两站

今日页（左侧「我的应用 → 今日」）只为这两站存在，它整页只画一块内容：**要你拍板**。定稿行右边是「看原帖」「改字」「定稿批准」，发布行是「看原帖」「看正文」「改字」「发布」——**两个按钮，两次点击，都不用填地址**。

地址为什么不用你填：现在的界面不问你，是因为**发出去这件事不在这一页发生**。第二下点完，稿子状态变成 `queued`（待发布），从你要办的事里消失，进发布队列——**地址由真正把它发出去的那一方回填**，不是你。

**边界说清楚**：队列、状态、看板这一层是真的；「地推员下一班自己按站点按钮发出去」这一步**还没接通**。地推员这个岗位现在的产出是把定稿话术备成每个位置的现场版（它自己汇报里也写明「本轮备好 N 条待发布，实际发布 0 条」）。真正发出去的路，目前是这两条：你自己复制粘贴，或者用 `node apps/desktop/test/manual/staff-publish-live.mjs` 让脚本借用已登录的窗口替你打字——**目前只接通了知乎**。

| 你做的事 | 在哪 | 之后自动发生什么 |
| --- | --- | --- |
| 点「定稿批准」 | 今日页，原地完成 | 这行当场变成「发布」行，并写明第二步还差什么 |
| 想先读一遍或改一个字 | 今日页「看正文」，正文就地展开、就地能改 | 不用跳页；要翻全部版本再点「改字」进内容工厂 |
| 点「发布」 | 今日页，按一下 | 状态转 `queued`（待发布），这行从你要办的事里消失，进发布队列 |
| 批复建议箱 | 今日页 | 中层的上报要么被采纳变成派单，要么被否掉 |
| 处理「卡住了」 | 今日页顶上的红条 | 通常是站点掉登录，扫个码就好 |

待发布的稿子在**内容工厂**里单独一列「待发布」。发出去、地址回填之后状态转 `published`，**回音巡检从那一刻开始读它**：谁在下面回复，谁就单独长成一张线索卡。所以那一列也是你手动发完之后回填地址的地方：点「标记已投放」，把地址贴上。

其余的东西收在一条「机器在跑」里：几个在岗、今天跑了几轮、有没有卡住。点开才展开九个员工的排期、两个常驻循环和最近一轮的分步明细——它们不需要你动手，所以不占版面。没有卡住的事时，连红条都不画。

剩下的：巡站、分级、选题、写稿、回音、接洽、成交、交付——**都不经过你**。

## 8. 数据落在哪张表

员工之间靠行交接，所以每张表都有明确的**唯一写入者**。数据页读的就是这张表：

| 表 | 谁写 | 里面是什么 |
| --- | --- | --- |
| `employee_runs` | 引擎 | 每一轮的步骤日志和结论（47 行） |
| `staff_leads` | 侦察员、回音巡检、接线员、跟单员 | 线索卡（11 行） |
| `staff_contents` | 笔杆子写稿、你改状态 | 稿件，含已归档的 68 篇 |
| `staff_suggestions` | 中层上报 | 要你定的建议（10 条） |
| `staff_directives` | 中层派单 | 工单（含期限和结果） |
| `staff_decisions` | 中层判断 | 判断本身 + 它依据的行 |
| `memory_items` | 全体 | 共享记忆（生效 5 条，已归档 25 条） |
| `staff_metrics` | 回音巡检 | 话题每天的数字 |
| `staff_sites` | 你（扫码登录） | 站点会话状态 |

**巡站那一站不落库**——读到的页面当次用完即弃。这不是省事，是设计：页面内容进了提示词就没有保留的必要，留着只会让库变大、让看板淹在历史里。数据页对那一行的体积写的是"—"而不是"0"，因为"0"读起来像故障。

## 9. 什么时候会停下来

| 情况 | 会发生什么 |
| --- | --- |
| 站点掉登录 | 巡站站变红，写清是哪个站；今天页进"卡住了" |
| 员工连续失败 | 退避重试：5 分钟起，每次翻倍，**最长 6 小时后**再试 |
| 工单过期 | 直接标失败，不迟到执行 |
| 撞到 `humanGate` | 这一轮立即中断，记 `HUMAN_GATE` |
| 同一时刻太多人 | 同时最多 2 个员工在跑，其余排队等下一轮 |
| 一天跑太多次 | 每个员工有自己的日配额；没写配额也有 96 次兜底 |
| 卡片解析失败 | 丢掉那几张，记日志，其余照常落库 |
